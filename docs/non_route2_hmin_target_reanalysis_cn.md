# 非 Route 2 路线冲击 `H_min >= 2` 的重新分析

## 1. 这次重新分析要回答什么

现在假设 `route2` 先搁置，只讨论另外三条路线：

- `route1`：2022 steering 协议；
- `route3`：CV 硬件风格 + 单设备 MDI 认证；
- `route4`：phase-insensitive APD 路线。

问题不是“它们有没有研究价值”，而是更直接的一句：

```text
只靠继续扫描参数，
它们有没有现实希望把认证后的 H_min 推近甚至推到 2？
```

这次我把结论分成两层：

1. 先看理论结构上有没有明显瓶颈；
2. 再看现有代码里往更激进方向推参数，数值上到底能涨到哪里。

## 2. 先给结论

先给清楚结论，再展开细节：

1. `route1` 不是完全不涨，但它现在显示出的趋势更像“还能往 `1.3 - 1.5 bit` 再推一点”，而不是“靠继续扫参就有望冲到 2 bit”。
2. `route3` 在当前“固定振幅、只扫相位”的 trusted input 设计下，存在明确的线性张成瓶颈。这个瓶颈不是多扫几个 `mu`、多加几个 phase 就能解决的，因此它目前不适合再被当成冲击 `2 bit` 的路线。
3. `route4` 的情况更极端：
   - 如果只看最宽松的“输出分布上界”，当 `N` 很大时它甚至能形式上超过 `2 bit`；
   - 但一旦回到正式认证，单输入会直接塌到几乎 `0 bit`，双输入在目前最好的已验证点也只有大约 `0.53 bit`；
   - 更大的 `N` 还会迅速触发更多 exact-zero / mixed-zero 病理，数值与建模都变得更差。
4. 因此，若 `route2` 暂时不能走，那么三条非 route2 路线里：
   - 最有现实希望继续往上推的是 `route1`；
   - 但它目前也没有显示出一条可信的数值路径能逼近 `2 bit`；
   - `route3` 和 `route4` 更像是“结构上就不该再指望单纯扫参把认证熵抬到 2”。

一句话概括：

```text
在“只改参数、不改路线结构”的前提下，
我现在看不到 route1 / route3 / route4 中任何一条
有可信路径能把认证后的 H_min 推到 2。
```

但三条路线里，`route1` 仍然是最值得继续做“接近目标”尝试的那条。

## 3. Route 1：不是完全没涨，但离 2 仍然远

### 3.1 理论上为什么它还能涨一点

`route1` 的核心是：

- 高斯纠缠源；
- Alice 做 `q/p` 周期 coarse-graining；
- Bob 做受信 homodyne 或 tomography；
- 用 steering SDP 认证 Alice 输出的随机性。

从理论上看，它不是被一个非常硬的上界直接卡死。原因是：

1. Alice 的输出数 `o_A` 可以继续增大；
2. squeezing 可以继续提高；
3. 总效率 `eta` 越接近 1，steering 约束越强；
4. Bob 的受信测量越接近 tomography，上界越高。

所以严格说，`route1` 不是“不可能涨”，而是“涨得很慢，而且代价非常高”。

### 3.2 结构性问题在哪里

问题主要有三层：

1. 它本质上还是高斯 steering 路线。
   - 这类路线更容易稳定拿到中等随机性；
   - 但并不天然擅长把认证熵冲到特别高。
2. Alice 只有两组互补测量 `q/p`。
   - 你可以加 coarse-graining bin 数；
   - 但 steering SDP 对这些 bin 的利用效率并不会无限线性增长。
3. Bob 端哪怕增加更多 homodyne 设置，也只是逐渐逼近 tomography。
   - 一旦 `m_B` 已经和 tomography 很接近，再继续加设置数，提升会越来越小。

换句话说，`route1` 的难点不在“参数还没扫够”，而在：

```text
当前这套物理资源和认证结构本身，更像中高熵路线，
不像靠调参就能冲到 2 bit 的高熵路线。
```

### 3.3 现有旧结果

此前已有结果里，比较激进的点是：

- `dimension = 5` 时，`H_min ≈ 1.0622`
- `dimension = 6` 时，`H_min ≈ 1.1671`

这些都还是明显低于 `2`。

### 3.4 这次重新做的更激进检查

我这次重新往更激进方向推了一个点：

- `source = tmsv`
- `bob_mode = homodyne`
- `dimension = 6`
- `squeezing_db = -8 dB`
- `eta = 1.0`
- `num_alice_bins = 10`
- `num_bob_bins = 12`
- `num_bob_settings = 6`
- `T_q ∈ {4, 6, 8}`

得到：

- `H_min ≈ 1.3183`
- 最优 `T_q ≈ 6.0`

然后继续把 squeezing 推到 `-10 dB`：

- 同样参数下得到 `H_min ≈ 1.3937`

再把 Alice 的分箱从 `10` 提到 `12`，并固定在此前最优 `T_q = 6.0` 做单点检查：

- `dimension = 6`
- `squeezing_db = -10 dB`
- `eta = 1.0`
- `num_alice_bins = 12`
- `num_bob_bins = 12`
- `num_bob_settings = 6`
- `T_q = 6.0`

得到：

- `H_min ≈ 1.4267`

### 3.5 这说明什么

这说明两件事：

1. `route1` 的确还可以继续涨；
2. 但它现在显示出来的是“慢慢从 1.1 往 1.4 走”的趋势，而不是“正在靠近 2”。

而且要注意：

- 这里已经用了非常理想的 `eta = 1.0`；
- squeezing 已经推到 `-10 dB`；
- Alice 分箱数也在增加；
- 计算时间已经明显变长。

所以这条路线当前最合理的判断是：

```text
可以继续冲击 1.5 左右，
但没有显示出一条可信的调参路径会把它推到 2。
```

### 3.6 如果还要继续扫，优先扫什么

如果实验室坚持再把 `route1` 往上顶一顶，最值得继续扫的是：

1. `squeezing_db`
   - 继续试 `-10 dB` 到 `-12 dB`
2. `num_alice_bins`
   - 继续试 `12, 14, 16`
3. `dimension`
   - 继续试 `6, 7`
4. `T_q`
   - 重点盯住 `T_q ≈ 6` 附近做细扫，而不是粗扫很大范围
5. `num_bob_settings`
   - 保持 `6` 或最多到 `8`
   - 不建议无限加，因为收益大概率会很快饱和

当前最值得继续延伸的参数起点是：

```text
source = tmsv
bob_mode = homodyne
dimension = 6
squeezing_db = -10 dB
eta = 1.0
num_alice_bins = 12
num_bob_bins = 12
num_bob_settings = 6
T_q ≈ 6.0
```

但我不建议把这条路线再当成“冲击 2 bit”主线，而更适合当成：

```text
非 route2 路线里最可能继续提高一点的方案
```

## 4. Route 3：当前结构下存在明确张成瓶颈

### 4.1 这条路线的关键不是 `mu`，而是 trusted input 的结构

`route3` 当前的 trusted input 族是：

- 固定振幅；
- 只扫相位；
- 每边是若干个相位相干态。

这看上去很自然，也很贴近 CV 硬件直觉，但它在单设备 MDI 认证里有一个非常关键的问题：

```text
它不是信息完备输入，
而且不是“差一点点不完备”，
而是先天地不可能靠单纯增加相位数变成信息完备。
```

### 4.2 为什么会这样

设本地截断维度为 `d`，固定振幅为 `|alpha|`，只改变相位 `phi`，则局域态在 Fock 基下的矩阵元形如

```text
rho_nm(phi) ∝ c_n c_m^* exp[i (n-m) phi]
```

也就是说，随相位变化真正变化的，只是差分频率 `n-m`。

于是：

- 局域密度矩阵随相位扫描能张成的独立方向，最多只和 `n-m` 的取值个数有关；
- 也就是最多大约 `2d - 1` 个独立方向；
- 而完整的局域算符空间维度是 `d^2`。

因此只要 `d > 2`，就一定有

```text
2d - 1 << d^2
```

所以当前 route3 的 trusted input 家族不可能成为真正的信息完备输入。

### 4.3 这次我直接做了线性张成检查

我用现有代码直接检查了不同 `cutoff` 和 `num_phases` 下的张成秩，结果非常清楚：

例如：

#### `cutoff = 4`

- `local_rank = 4`
- 局域完整算符空间维度应为 `16`
- 但 local operator span 最多只到 `7`
- joint operator span 最多只到 `49`
- 而 joint operator space dimension 是 `256`

并且当 `num_phases` 从 `8` 加到 `12`、`16`、`24` 后：

- `operator_span_rank` 不再增加；
- 始终卡在 `49`。

#### `cutoff = 6`

- 局域完整算符空间维度是 `36`
- 但 local operator span 最多只到 `11`
- joint operator span 最多只到 `121`
- 而 joint operator space dimension 是 `1296`

这说明：

```text
route3 当前的相位态输入族，
在结构上就给不出足够强的单设备 MDI 约束。
```

这不是多扫 `mu` 能解决的。

### 4.4 这次做的更激进数值点

我继续往更激进方向推了几组：

- `cutoff = 4`
- `num_phases = 8, 12, 16`
- `num_x_bins = 2`
- `num_p_bins = 4`
- `mu = 0.05, 0.1, 0.2, 0.5`

结果里比较高的点是：

- `mu = 0.05`
- `cutoff = 4`
- `num_phases = 8`
- `2 x 4` 输出
- `raw_H_min ≈ 2.040`
- `certified H_min ≈ 0.6671`

然后继续把相位数加到 `12`、`16`：

- `operator_span_rank` 仍然卡在 `49`
- `certified H_min` 基本不再有实质提升

也就是说：

```text
route3 现在的问题不是 raw 熵不够，
而是认证时约束不够强。
```

这正是 operator span 瓶颈的直接数值表现。

### 4.5 Route 3 的结论

在当前路线定义下：

- 多扫相位数没有本质帮助；
- 多扫 `mu` 也没有本质帮助；
- raw 熵可以过 2；
- 但 certified 熵会被严重拉回去。

因此我现在的判断是：

```text
只靠继续扫描 route3 当前这些参数，
没有现实希望把认证 H_min 推到 2。
```

如果以后要救这条路线，方向不应该是“继续加 phase”，而应该是：

- 改 trusted input 家族；
- 不再只用固定振幅的 phase-only alphabet；
- 让局域输入态的算符张成尽量逼近信息完备。

但那已经不是“只调 route3 参数”，而是在改路线结构了。

### 4.6 如果只是想把 route3 推到当前结构下的最好状态

可以把下面这组当成当前较好的参考点：

```text
mu = 0.05
cutoff = 4
num_phases = 8
num_x_bins = 2
num_p_bins = 4
```

这时：

- `raw_H_min ≈ 2.04`
- `certified H_min ≈ 0.667`

它说明 route3 还能做一些“硬件风格保持不变”的探索，但不适合继续当成冲击 `2 bit` 的方向。

## 5. Route 4：分布上界能涨，但正式认证会塌

### 5.1 这条路线要分清“分布上界”和“正式认证”

`route4` 最容易误判的地方在于：

- 只看输出分布时，随着 coarse-graining 输出数 `N` 增大，最大输出概率会下降；
- 于是 `distribution_only_H_min` 会显著上升；
- 但这只是最宽松上界，不是正式认证值。

正式认证还要满足：

- phase-insensitive；
- Fock 对角；
- 多输入一致性；
- Eve 最优猜测的 LP 约束。

而这些约束一加进去，结果会明显塌下来。

### 5.2 这次先看最宽松上界

我先扫了单输入情形下的最宽松“输出分布上界”。

结果非常有意思：

- `N = 16` 时，最佳单输入上界大约 `1.445 bit`
- `N = 24` 时，上界大约 `1.947 bit`
- `N = 32` 时，上界大约 `2.326 bit`
- `N = 64` 时，上界大约 `3.299 bit`

最佳单输入通常来自：

- `mu = 160`

这说明：

```text
从“输出分布是否足够铺开”这件事本身看，
route4 并不是在所有大 N 下都绝对不可能超过 2。
```

但这只是第一层。

### 5.3 一旦回到正式认证，单输入会直接塌掉

我进一步把单输入直接送进正式 dual 认证，取：

- `selected_mu_list = [160]`
- `q = [1.0]`

结果是：

- `N = 16`：`H_min ≈ 0`
- `N = 24`：`H_min ≈ 0`
- `N = 32`：`H_min ≈ 0`
- `N = 48`：`H_min ≈ 0`
- `N = 64`：`H_min ≈ 0`

哪怕对应的 distribution-only upper bound 已经明显超过 `2 bit`，正式认证仍然塌到几乎 `0`。

这件事的物理含义非常重要：

```text
route4 不是“输出分布不够散”，
而是“在当前安全模型里，单输入根本约束不住 Eve”。
```

### 5.4 加入第二个输入后，正式认证能回升一些，但仍远离 2

我对一个目前比较好的双输入点做了正式认证：

- `selected_mu_list = [140, 160]`
- `q = [0.5, 0.5]`
- `N = 16`
- `cutoff = 280`

得到：

- `distribution_only_H_min ≈ 1.361`
- `certified H_min ≈ 0.527`

这比此前 route4 报告里的 `0.39` 又高了一点，说明：

- route4 不是完全不能涨；
- 通过改输入子集，确实还能从 `0.39` 推到 `0.53` 左右。

但这距离 `2 bit` 仍然差得非常远。

### 5.5 更大 `N` 的趋势并不乐观

我还检查了更大 `N` 的情况。

现象是：

1. distribution-only upper bound 继续升高；
2. 但正式 dual 问题开始更容易出现：
   - all-zero columns 增多；
   - mixed-zero columns 增多；
   - exact / regularized 问题更病态。

例如在一个近似检查里：

- 双输入 `[140,160]`
- `N = 24, 32`
- cutoff 降到较小但仍有参考意义的量级

dual 直接出现了 `unbounded`。

这不等于“真实答案一定是 0”，但它说明：

```text
随着 N 增大，route4 不仅没有显示出稳定迈向高熵，
反而越来越容易落入 exact-zero / 病态区域。
```

### 5.6 Route 4 的结论

因此 route4 当前最合理的判断是：

1. 单纯继续加大 `N`，确实会让“输出分布上界”看起来更漂亮；
2. 但这并不等于正式认证值会跟上；
3. 一旦加入真正的多输入认证约束，值会大幅回落；
4. 而更大的 `N` 还会加重病态与零概率问题。

所以：

```text
route4 可以继续当“平台诊断路线”往前做，
但它没有显示出靠参数扫描逼近 2 bit 的可信路径。
```

### 5.7 如果还想把 route4 推到当前结构下的相对最好状态

目前一个比旧报告更好的已验证点是：

```text
selected_mu_list = [140, 160]
q_selected = [0.5, 0.5]
N = 16
cutoff = 280
prob_floor = 1e-12
```

对应：

- `certified H_min ≈ 0.527`

这可以作为 route4 当前更强的参考点，但它仍明显不属于“接近 2”的范围。

## 6. 三条路线横向比较

### 6.1 理论结构上

- `route1`
  不是被严格上界卡死，但当前高斯 steering 结构涨得慢。
- `route3`
  当前 fixed-amplitude phase-only trusted input 先天地不信息完备，存在明确 operator-span 瓶颈。
- `route4`
  输出分布上界能涨，但正式认证约束一下就塌，而且大 `N` 时病态迅速加重。

### 6.2 数值上目前最好的已确认点

- `route1`
  - `H_min ≈ 1.4267`
  - 条件：`dimension=6`, `squeezing=-10 dB`, `eta=1`, `o_A=12`, `o_B=12`, `m_B=6`, `T_q=6`
- `route3`
  - `H_min ≈ 0.6671`
  - 条件：`cutoff=4`, `num_phases=8`, `mu=0.05`, `2x4` 输出
- `route4`
  - `H_min ≈ 0.5273`
  - 条件：`N=16`, `selected_mu_list=[140,160]`, `q=[0.5,0.5]`

### 6.3 距离 2 的相对位置

- `route1`
  最接近，但仍差大约 `0.57 bit`
- `route3`
  还差大约 `1.33 bit`
- `route4`
  还差大约 `1.47 bit`

## 7. 最后的建议

如果 `route2` 现在必须暂时放下，那么我建议这样分配精力：

### 7.1 第一优先级：继续推 `route1`

原因不是它有望到 2，而是：

- 它是三条里唯一还显示出稳定上涨趋势的；
- 它的物理图像最清楚；
- 它最有机会把“非 route2 路线的上限”继续往上推一点。

建议继续扫的参数是：

- `dimension = 6, 7`
- `squeezing_db = -10, -11, -12`
- `num_alice_bins = 12, 14, 16`
- `num_bob_bins = 12, 16`
- `num_bob_settings = 6, 8`
- `T_q` 重点扫 `5.5 - 6.5`

但这里的预期目标应该改成：

```text
看能不能把 route1 推到 1.5 左右，
而不是默认还能冲到 2。
```

### 7.2 第二优先级：停止把 `route3` 当成“靠调参能救活”的路线

如果继续做 route3，我建议把目标从“冲击 2 bit”改成：

- 作为结构性反例；
- 明确证明“phase-only alphabet 在单设备 MDI 下为什么不够”；
- 为后续改 trusted input 设计提供依据。

也就是说，route3 若继续做，重点应该从“扫参数”改成“改输入族结构”。

### 7.3 第三优先级：`route4` 作为平台诊断继续保留，但不再指望它接近 2

route4 仍然有价值，因为它直接贴着现有 APD 数据。

但若目标写成：

```text
H_min >= 2
```

那么 route4 不应再作为主攻方向。

它更适合回答的问题是：

```text
现有 APD 平台在这套安全假设下，
到底最多能认证到什么量级？
```

## 8. 一句话总结

如果只保留一句话，这次重新分析的结论是：

```text
在不改路线结构、只继续扫描参数的前提下，
route1 / route3 / route4 里没有哪一条显示出可信路径能把认证后的 H_min 推到 2；
其中 route1 还值得继续冲更高一些，
但 route3 和 route4 基本已经不是“再扫一轮参数就可能接近目标”的状态。
```
