# “高速 CV 前端 + 数字 coarse-graining + route2 SDP”混合方案分析

## 1. 这份分析回答什么问题

这里讨论的不是当前 `route3` 原样能不能做到 `H_min >= 2`，也不是当前离散单光子版 `route2` 能不能直接满足实验室的 `10 Gbps` 目标。

这里讨论的是第三种东西：

```text
高速 CV 前端
+ 数字 coarse-graining
+ route2 单设备 MDI SDP
```

也就是：

- 硬件前端尽量沿用实验室更擅长的高速连续变量接收；
- 后端把连续 IQ / dual-homodyne 输出切成有限个离散结果 `c`；
- 安全分析不再回到旧的局域拆分，而继续使用 route2 的单设备 MDI 认证。

核心问题有两个：

1. 这条混合路线在物理上是否可行？
2. 它是否有现实希望把认证最小熵推到 `H_min >= 2`？

## 2. 先说结论

先给出最简洁的结论。

1. 从器件带宽和系统架构角度看，这条混合方案是物理上可行的，而且比离散单光子版 route2 更贴近实验室高速目标。
2. 从安全结构角度看，它也是合理的，因为 route2 的 SDP 本来只要求可信输入、中央黑盒测量和离散统计 `P(c|x,y)`，并不要求中央测量必须是点击式单光子探测器。
3. 但当前仓库里的数值证据还不足以宣布它已经能做到 `H_min >= 2`。
4. 现有 `route3` 结果之所以只有 `0.55 - 0.66`，关键不是“CV 前端天然不行”，而是“`phase-only trusted inputs` + `粗粒化 dual-homodyne`”这组输入约束太弱。
5. 我用当前仓库代码做了额外检查，发现一旦 trusted input 从“只扫相位”升级为“同时扫振幅和相位”的相干态字母表，局域算符张成能力可以从明显欠完备，提升到真正的信息完备。
6. 这说明混合方案至少在结构上修掉了 route3 当前最大的瓶颈，因此 `H_min >= 2` 不能被视为“已经被 route3 否定”。
7. 但它也还不能被视为“已经很有把握能做到”。更准确的判断是：

```text
物理可实现性：中高
H_min >= 2 的可能性：中等、尚未证实
直接达到 >= 10 Gbps 认证输出带宽：目前仍未证实
```

## 3. 为什么它在物理上比离散单光子版 route2 更合理

### 3.1 它避开了点击式单光子探测的速率瓶颈

离散单光子版 route2 最自然的实验图景是：

- 单光子偏振 / 相位 / 时隙编码；
- 中央联合测量；
- 输出由单光子探测器点击模式给出。

这类实现会遇到：

- 死时间 / 恢复时间；
- 后脉冲、淬火、复位；
- 联合测量成功率和符合计数开销。

而混合方案把中央测量改成：

- beam splitter + dual-homodyne / heterodyne；
- 连续模拟输出；
- 高速 ADC；
- 数字域 coarse-graining。

这样中央接收机的瓶颈就从“单光子点击计数率”切换成了“模拟链路带宽、噪声和采样处理能力”，这与实验室追求 `GSa/s` 数据流的目标明显更匹配。

### 3.2 从当前商业器件看，带宽层面并不离谱

以公开商用器件为例：

- 官方现成的 LiNbO3 光调制器已经覆盖多 GHz 到几十 GHz 的高速调制范围；
- 官方现成的 balanced photoreceiver 也可以做到多 GHz 甚至更高带宽；
- `5 GSa/s` 乃至更高采样率的示波器 / ADC 平台本身也是现成能力。

这并不等于实验室已经具备完整闭环系统，但至少说明：

```text
“高速 CV 前端”这件事本身不是反物理的，
也不是明显超出现代光学链路能力边界的事情。
```

### 3.3 但“ADC 5 GSa/s”不等于“认证轮次就是 5e9 / s”

这一点必须反复强调。

即便前端物理上能做到 `5 GSa/s`，也不能直接把它写成：

```text
5 × 10^9 个独立认证轮次 / s
```

因为中间还隔着几层问题：

- 模拟样本之间的时间相关；
- 匹配滤波和抽样时钟定义；
- 轮次应该按脉冲、按符号，还是按 ADC 样点来定义；
- 生成轮 / 测试轮偏置；
- 有限尺寸统计损失；
- 提取器效率。

所以这条混合路线在物理上“能跑得快”，并不自动等于它在安全意义上“已经能给出 `>= 10 Gbps` 的认证输出”。

## 4. 当前 route3 为什么不能直接当成混合方案的证据

这一步很关键。

很多人会自然地说：

```text
既然 route3 已经是 CV 前端 + coarse-graining + 单设备 SDP，
而且它只有 0.6 bit 左右，
那混合方案大概也没戏。
```

这个推理并不成立。

原因是当前 `route3` 还有一个结构性限制：

- trusted inputs 基本是固定振幅、只扫相位的 coherent states；
- 这类输入集在算符张成上天然太弱；
- 所以即便 raw 直方图已经很平，Eve 仍然保有大量“看不见方向”的自由度。

也就是说，`route3` 现在真正否定的是：

```text
phase-only trusted inputs + dual-homodyne coarse-graining
```

而不是：

```text
CV 前端 + route2 认证
```

## 5. 我用当前仓库做的额外结构检查

为了判断混合方案是不是只停留在概念层面，我额外用仓库现有的

- `qrng_routes.common.coherent_state`
- `qrng_routes.common.support_basis`
- `qrng_routes.common.operator_span_rank`

做了一个局域张成检查。

检查目标很简单：

- 看 trusted coherent-state alphabet 在截断局域支撑上的 operator span 到底有多大；
- 比较“只扫相位”和“同时扫振幅与相位”的差别。

### 5.1 结果 1：phase-only 输入确实严重欠完备

代表性结果如下。

对 `cutoff = 5`：

- 6 相位时，局域 support 维数是 `5`，但 operator span 只有 `6`，而完整算符空间维数是 `25`。
- 8 相位时，operator span 只有 `8 / 25`。
- 10 相位时，operator span 也只有 `9 / 25`。

对 `cutoff = 6`：

- 6 相位时，operator span 只有 `6 / 36`。
- 8 相位时，只有 `8 / 36`。
- 10 相位时，也只有 `10 / 36`。

这和我们之前对 route3 的理论判断是一致的：

```text
只扫相位，输入约束能力会明显不足。
```

### 5.2 结果 2：加入振幅自由度后，局域信息完备是可做到的

我又测试了“振幅 + 相位”的 coherent-state 字母表。

结果是：

- 对 `cutoff = 5`，随机选取 `25` 个振幅-相位不同的 coherent states，就已经能达到局域满张成 `25 / 25`。
- 对 `cutoff = 6`，随机选取 `36` 个振幅-相位不同的 coherent states，就已经能达到局域满张成 `36 / 36`。

这件事非常重要。它说明：

```text
只要 trusted inputs 真正覆盖二维相空间，
相干态字母表本身并不会先天地卡死在“非信息完备”状态。
```

也就是说，混合方案不是在空想一个“CV 前端但输入仍然太弱”的版本，而是确实可以在结构上修补 route3 当前最大的缺口。

### 5.3 但这同时带来一个现实代价

局域输入一旦要做到接近信息完备，输入字母表数量会明显增加。

例如：

- 若有效局域维数是 `d = 5`，一般至少要考虑 `d^2 = 25` 个左右线性独立输入算符；
- 若有效局域维数是 `d = 6`，则大约要 `36` 个左右。

这并不意味着实验每拍都要随机切换几十个输入态，但它意味着：

- 测试轮设计会更复杂；
- 参数估计开销会更大；
- 有限尺寸压力会更重。

因此，混合方案虽然在输入结构上更强，但它不是“免费增强”。

## 6. 对 `H_min >= 2` 的判断应该怎么做

现在可以把现有证据拼起来。

### 6.1 已知的两端证据

一端是当前 route3：

- 物理测量结构比较现实；
- 但因为 trusted inputs 太弱，认证后只有大约 `0.55 - 0.66`。

另一端是当前 route2：

- trusted inputs 很强；
- 单设备 SDP 也正确；
- 但高输出结果来自自由 POVM 搜索，还没有施加真实高速接收机约束；
- 数值上可以到 `H_min > 2`。

因此混合方案处在两者之间：

- 它比 route3 的输入约束更强；
- 但比 route2 的自由 POVM 更受物理实现限制。

这意味着它的真实地位应当表述为：

```text
H_min >= 2 没有被现有证据否定，
但也还没有被现有证据证明。
```

### 6.2 为什么它“有希望”，而不是“只是幻想”

我认为它有希望，主要基于三点。

第一，当前 route3 的主要失败点是“输入不够强”，而不是“CV 前端一定不行”。

第二，当前 route2 已经证明：只要输入约束足够强，单设备 MDI 模型下的高熵空间是真实存在的。

第三，我刚做的局域张成检查说明：coherent-state alphabet 在幅相联合设计下，的确可以做到局域信息完备，而不是被相干态家族本身卡死。

因此，从结构上讲，混合方案至少满足下面这条逻辑链：

```text
高速 CV 前端是物理上可行的
且
相干态 trusted inputs 可以设计成信息完备
且
route2 安全框架允许中央输出先连续再 coarse-grain
=> 混合方案是一个真正值得做数值与实验联动优化的候选主线
```

### 6.3 为什么我还不能说“它大概率一定能过 2”

因为还有三道真正没被解决的关卡。

第一道：物理受限 POVM 的认证值是否还够高。

当前 route2 的 `> 2` 结果来自自由 rank-1 POVM 搜索，不是 dual-homodyne / heterodyne + IQ 分区约束下的结果。

第二道：近信息完备输入带来的测试开销是否会吞掉净带宽。

即便生成轮单轮熵很高，测试轮比例、有限尺寸和提取效率也会把平均输出速率拉低。

第三道：真实高速链路中的相关性处理。

只要轮次定义、滤波、下采样和 i.i.d. 近似没有处理清楚，就不能把实验 ADC 速率直接翻译成安全意义上的带宽。

所以对 `H_min >= 2` 最准确的说法应当是：

```text
中等可行，但当前仍属“待证实目标”，不是“已基本坐实的结论”。
```

## 7. 对实验室而言，这条混合路线到底值不值得做

我的判断是：值得，而且比离散单光子版 route2 更值得。

但要明确它的定位。

### 7.1 它最适合作为“主线候选”的原因

因为它同时继承了两边的优点：

- 继承 route2 的高熵安全框架；
- 继承 route3 的高速 CV 硬件外形。

这正好对应实验室当前最关键的双重目标：

- 想保住高速；
- 又不想放弃高熵认证的希望。

### 7.2 它不适合作为“马上能交付的成熟方案”的原因

因为它现在还缺三块关键工作：

1. 物理约束下的高输出优化
2. 测试 / 生成轮速率模型
3. 有限尺寸与相关性分析

所以这条路最准确的定位不是：

```text
已经成熟，可以直接上机做 10 Gbps 认证实验
```

而是：

```text
最值得作为下一阶段主攻的协议-硬件共设计方向
```

## 8. 最值得立刻做的下一步

如果要把这条混合路线真正推进，我建议下一步集中做四件事。

### 8.1 把 route3 改成“广义 coherent alphabet”

不要再把 trusted inputs 限死为 phase-only。

应该改成：

- 输入集合由任意复振幅 `alpha_k` 给出；
- 每边允许同时扫描振幅和相位；
- 程序直接输出 local span rank / operator span rank。

这是最重要的第一步，因为它决定协议结构是不是仍旧先天偏弱。

### 8.2 对 IQ 平面分区做真正优化

不要只固定简单矩形 binning。

应该尝试：

- 4 / 8 / 12 / 16 输出；
- 非均匀边界；
- 针对生成输入最优的区域划分；
- 但仍保持 dual-homodyne / heterodyne 这一物理结构不变。

### 8.3 引入测试轮 / 生成轮偏置

不要再把所有输入平均使用。

应当分成：

- 少量测试轮：覆盖信息完备输入集；
- 大量生成轮：固定在一两个最优输入。

只有这样，混合方案才有现实希望把高输入数带来的统计压力控制住。

### 8.4 在代码里直接输出平均认证速率

下一版代码不应只给 `H_min`，还要给：

- `q_test`
- `f_round`
- `eta_ext`
- `R_out`

这样才能真正回答实验室的问题：

```text
这条混合路线不是单轮能不能过 2，
而是整套协议最后每秒到底能不能给出 >= 10 Gbps 的认证随机数。
```

## 9. 最终判断

如果把判断压缩成一句话，那么我的结论是：

```text
“高速 CV 前端 + 数字 coarse-graining + route2 SDP”是物理上可行、协议上合理、而且最值得继续深推的混合主线；
但它目前仍处在“有明确希望但尚未数值证实 H_min >= 2”的阶段。
```

再拆成更适合决策的三句话：

1. 作为替代离散单光子版 route2 的方案，它是值得做的。
2. 作为冲击 `H_min >= 2` 的方案，它是有希望的，但当前证据还不够。
3. 作为直接承诺 `>= 10 Gbps` 认证输出带宽的方案，现在还远不到能下保证的时候。
